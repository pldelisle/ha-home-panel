# Spec 07: npm packages replace the committed vendor files

Parent: [production-grade-refactor.md](production-grade-refactor.md), phase 1.
Depends on: [06 Vite build](06-vite-build.md). Independent of [08 bundled font](08-bundled-font.md).
Ships as: one pull request, a patch release, no visible change.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be read as in RFC 2119.

## Problem Statement

ApexCharts 3.45.2, Leaflet 1.9.4 and Mermaid 11.4.1 are committed as minified files under `vendor/` (3.2 MB) and copied beside the bundle at build time. Nothing tells the maintainer about a security fix; the versions in the licences file are maintained by hand; and Leaflet turns out to be unused by the panel itself (the radar map comes from the Weather Radar Card, which brings its own Leaflet), so 150 KB ships for nothing. The lazy loading works by appending `<script>` tags for files found next to the bundle, which ties the file names to the loader.

## Solution

Install ApexCharts and Mermaid from npm at the versions used today, load them with dynamic `import()` so Vite emits them as lazy chunks, drop Leaflet, delete the `vendor/` directory, and generate the licences table from the installed packages. ApexCharts is pinned to its 3.x major, and Renovate is told to ignore its majors because later lines are dual-licensed.

## User Stories

1. As a maintainer, I want Renovate to tell me about a patch to Mermaid or ApexCharts, so that security fixes are not something I have to remember to check.
2. As a maintainer, I want the licences file to be correct by construction, so that it cannot drift from what ships.
3. As a household member, I want the panel not to download a library it does not use, so that the tablet loads less.
4. As a maintainer, I want the chart and diagram libraries to remain lazy, so that the Home tab does not pay for the Automations tab.
5. As a maintainer, I want ApexCharts kept at the last plain-MIT line and protected from an accidental upgrade, so that the repository's MIT licence stays simple.

## Implementation Decisions

### Packages

- `apexcharts` at exactly `3.45.2` (no caret). `mermaid` at the current `11.x` release (caret allowed; Renovate tracks it). Both as `dependencies`, not `devDependencies`, so the licence tooling sees them as shipped. Amended in #37: `mermaid` is pinned at exactly `11.4.1`, the version that was vendored, and Renovate tracks it in a group of its own (see "As built (#37)").
- Leaflet is NOT installed. `vendor/leaflet.js` and `vendor/leaflet.css` are deleted, the README credit line for Leaflet is removed, and the dist test stops expecting them. The PR description MUST state the verification: `grep -rn leaflet src/` returns nothing before and after.
- The `vendor/` directory and `vendor/LICENSES.md` are deleted.

### Lazy loading

- The `loadScript` helper and its `<script data-home-panel>` mechanism are deleted. The class obtains ApexCharts with `const {default: ApexCharts} = await import('apexcharts')` at the point where it awaited `this.apex` before, and keeps a module-level promise so the import happens once. All references to `window.ApexCharts` are replaced by the imported binding.
- ApexCharts' stylesheet is imported as text (`apexcharts/dist/apexcharts.css?raw`) inside the same lazy module and injected into the existing `#apexcss` style element, replacing the `fetch(BASE + 'apexcharts.css')`. Amended in #73: the panel does not import or inject the stylesheet at all; ApexCharts writes its own (see "As built (#73)").
- Mermaid is obtained with `const {default: mermaid} = await import('mermaid')` where `loadScript(BASE + 'mermaid.min.js')` was, replacing `window.mermaid`. Mermaid's `initialize` call and its `securityLevel: 'strict'` setting are unchanged.
- Vite emits each as a chunk under `dist/chunks/`. The two lazy modules MUST be separate chunks from the entry and from each other; the chunk file names carry a content hash so the HTTP cache needs no `?v=`.
- The static copy plugin from spec 06 is removed.

### Licences

- `vendor/LICENSES.md` is replaced by `LICENSES.md` at the root, generated by `npm run licenses`, which uses `license-checker-rseidelsohn` (or an equivalent that reads `package-lock.json`) restricted to production dependencies and writes a table with package, version, licence and repository URL, followed by the full licence text of each. The Montserrat font row is added by spec 08.
- A Vitest test reads `LICENSES.md` and asserts that every production dependency in `package.json` appears with the exact installed version from `package-lock.json`, so a bump without regeneration fails CI.
- The README's Credits section points at `LICENSES.md` and names ApexCharts and Mermaid only.

### Renovate

- The rule from spec 05 disabling `apexcharts` major updates is confirmed present. A second rule MAY group `mermaid` updates with the other minor and patch updates.

### Size

- The size budget from spec 06 applies to `dist/home-panel.js` only; the lazy chunks are not counted but their gzipped sizes MUST be printed by `npm run size` for information (ApexCharts about 135 KB, Mermaid about 750 KB today).

### Tests

- The dist test asserts: no `vendor` files in `dist/`; exactly one chunk whose content includes the ApexCharts banner and one whose content includes Mermaid's; the entry does not include either library.
- A Playwright behaviour test MUST assert that loading the Home tab triggers no request for a chunk containing ApexCharts or Mermaid, and that opening the Energy tab (charts) and the Automations tab (Mermaid) each trigger exactly one such request. The fixture's network recording is extended to capture chunk URLs for this.
- The screenshot baselines MUST pass unchanged.

## Acceptance Criteria

1. `vendor/` does not exist; `package.json` lists `apexcharts` at `3.45.2` exactly and `mermaid` at `^11`; `grep -rn "leaflet" src test README.md` returns nothing. Amended in #37: `mermaid` is pinned at exactly `11.4.1`, the version that was vendored, because every 11.x from 11.10 moves the Automations flow charts by a few hundred pixels and the ones before it carry the same advisories; see "As built (#37)".
2. `npm run build` emits `dist/home-panel.js`, its map and at least two chunks; the Home tab loads none of the chunks and the Energy and Automations tabs load one each (Playwright test green). Amended in #37: the Automations tab loads Mermaid's chunk graph, 24 requests of which one holds its core; the Energy tab loads ApexCharts' one chunk; the Home tab loads none.
3. `LICENSES.md` exists at the root, is generated, and the licence test passes; bumping Mermaid in `package.json` without regenerating makes the test fail. Amended in #38: the generated file also ships inside `dist/`, and so in the release zip, on purpose; see "As built (#38)".
4. The visual project passes with no baseline updated; the behaviour suite passes.
5. `renovate.json` contains the ApexCharts major-update rule.

## Testing Decisions

Baselines prove the charts and flow diagrams draw as before. The chunk-loading test protects the lazy behaviour, which is the one thing this change could silently break. The licence test protects the drift this spec exists to end.

## Out of Scope

- Upgrading ApexCharts past 3.x or replacing it.
- Replacing Mermaid.
- Changing any chart option or diagram style.
- The Weather Radar Card dependency, which stays an external HACS card loaded from its Lovelace resource URL.

## Notes

- Mermaid 11 as an ES module is large and pulls in many sub-packages; Vite will split it into several chunks. That is acceptable. If chunk count becomes a problem for the harness server or the zip, use `build.rollupOptions.output.manualChunks` to keep Mermaid in one chunk.
- ApexCharts' package exports both ESM and UMD; make sure the ESM build is picked (Vite does by default) so tree shaking applies.
- Deleting Leaflet is a behaviour-neutral change only because the panel never referenced it; the radar sheet's "didn't load" note in the test house proves the radar comes from elsewhere.

## As built (#36, ApexCharts)

Where the ApexCharts part of the build differs from the plan above, and why. The plan stays as written; this is the record.

- **The npm files are the vendored files.** `apexcharts@3.45.2` was installed with `--save-exact` as a production dependency, and `dist/apexcharts.min.js` and `dist/apexcharts.css` in the package have the same SHA-1 as the two files that were in `vendor/` (`1107e401…` and `b82ac4fc…`), so what the panel runs is the code it ran before. `vendor/apexcharts.min.js` and `vendor/apexcharts.css` are deleted; `vendor/LICENSES.md` keeps an ApexCharts row (saying it is now an npm package) until #38 replaces the file.
- **The ESM file is imported by its path, not the package name.** The package has no `module` or `exports` field: `import('apexcharts')` resolves to `main`, `dist/apexcharts.common.js`, which is CommonJS. Vite then wraps it in a helper, which put a second chunk (`rolldown-runtime`, 0.6 KB) in the entry's static imports, so the Home tab fetched a chunk after all. `dist/apexcharts.esm.js` is the same release as an ES module (the package ships it, minified like the others), and `import ApexCharts from 'apexcharts/dist/apexcharts.esm.js'` needs no helper. Its one `typeof module` test, in the bundled svg.js, takes the same branch as the `<script>` build did (`window.SVG` is set), where the CommonJS wrapper would have taken the other. Rolldown warns `COMMONJS_VARIABLE_IN_ESM` about that line on every build; it is a warning about the package's code, not ours, so `onwarn` in `vite.config.ts` drops it when the file is under `node_modules/apexcharts/` and passes every other warning on. There is no tree shaking to lose: every build of the package is one pre-bundled file.
- **The stylesheet needs a module of its own to land in the chunk.** `import css from '…/apexcharts.css?raw'` in `src/charts/apex.js` put the 13 KB of CSS in the entry, because the entry imports `apex.js` statically (the fallback the ticket anticipated). `src/charts/apex-lib.js` imports the library and the stylesheet and re-exports both; `src/charts/apex.js` holds only `loadApex = () => (chunk ??= import('./apex-lib.js'))`. The chunk takes its name from that module. Amended in #73: the module imports the library only; the stylesheet is no longer imported (see "As built (#73)").
- **Chunk and entry sizes.** `dist/chunks/apex-lib-<hash>.js` is 530,222 bytes (135,140 gzipped at level 9; Vite prints 137.11 kB at its default level), the library plus the stylesheet. Amended in #73: the stylesheet was packed twice there (the `?raw` copy and the library's own); it is once now, and the chunk is 13 KB smaller. The entry was 505,433 bytes (144,592 gzipped at level 9) on `main` after #35 and is 506,127 (144,818) after: 694 bytes more, for the loader, the list of sheets that wait for the library, the guards below and the weather sheet's extra care. The source map of the chunk is 1,107,102 bytes and ships beside it.
- **Which sheets fetch it.** The old code started the script load in `build()`, as soon as the panel drew itself. Now `loadCharts()` runs in `buildSheet` for `sh-energy`, `sh-climate`, `sh-car`, `sh-air` and `sh-wx` only (`CHART_SHEETS` in `src/home-panel.js`), and the Weather sheet fetches it beside its history (`weatherSheet` awaits both with `Promise.allSettled`, each with its own message when it fails); the lights, camera, sensor and "more" sheets and the Home, Lights, Media, Cams and Automations panes draw no chart and do not wait for the library. The sheets that `buildSheet` draws run after that await, but a tap (a range tab, a purifier control) or a Home Assistant update can reach a chart-drawing method while the chunk is still loading, and `this.ApexCharts` is then still `null`. `energyMain`, `airChart`, `airOutChart`, `wxSheet` and `climateSheet` therefore return at once until it exists (`buildSheet` draws the sheet when the chunk lands, with whatever range the tap chose), and `renderForecast` and `climateDetail` already tested it. A weather sheet closed, or closed and opened again, while the chunk is loading is drawn once, by the visit that is still open (`weatherSheet` keeps `buildSheet`'s tag). The stylesheet is written into `#apexcss` by `applyApexCss()`, from `loadCharts()` and again from `build()`, so a rebuilt panel (a language or config change) keeps it. Amended in #73: `#apexcss` and `applyApexCss()` are gone; the library writes its own stylesheet each time a chart mounts, so a rebuilt panel has it as soon as its charts are drawn.
- **Why the Weather sheet does not wait for the library before it renders.** The first version put `sh-weather` in `CHART_SHEETS`. The bare house opens Weather as its first chart sheet, so the pane stood on screen, empty of charts, while the chunk was fetched, and its screenshot came out 1 px different on the three static lines of text under "Radar", "Next 24 hours" and "Next days" (the layout rectangles were identical; only the raster differed, every time, and not when the library was loaded at start-up). A baseline must not change, so the sheet now renders its tiles and forecast at once, exactly as before, and the library arrives in parallel with the history it already waited for. If an hourly forecast is there before the library, `renderForecast` fetches it and draws the hourly chart when it lands (checked by hand; the harness has no forecast subscription, so no spec reaches that path).
- **Failure is as before, and permanent as before.** A failed import rejects the same way a failed script load did, and `buildSheet` shows the same toast, "Charts library failed to load". The old code kept the rejected promise for the life of the page, and so does this: Chromium remembers a failed module URL, so clearing the promise would not make a second `import()` fetch again (tried, and the test for it failed), and only a reload recovers, as before.
- **The URL.** A dynamic import resolves against the importing module, so `chunks/apex-lib-<hash>.js` is found beside `home-panel.js` wherever Home Assistant serves it, and the `?v=` on the entry does not carry over to the chunk; its hash is its cache key. Checked with `dist/` served at `/hacsfiles/ha-home-panel/` and the entry loaded as `home-panel.js?v=2.11.1`: no chunk request on Home, `/hacsfiles/ha-home-panel/chunks/apex-lib-….js` once on Energy, the chart drawn, no console error.
- **The release zip.** `release.yml` zips `dist/` with `zip -r` from inside it and compares `find . -type f` with `unzip -Z1` after dropping directory entries; run locally on this build, the lists are equal with `chunks/` in them (`chunks/apex-lib-….js` and its `.map`), so the workflow needed no change.
- **Tests.** `dist.test.mjs` lists `dist/` recursively: the entry, its map, the vendored files that remain, and chunks with their maps; exactly one chunk holds the library (found by a class name only its drawing code uses, because the minifier drops the banner comment) and the stylesheet text; the entry holds neither and reaches the chunk with `import('./chunks/apex-lib-….js')`. Amended in #73: the test now asserts that the stylesheet is in the shipped files once, not that the chunk holds it. `test/e2e/chunks.spec.ts` uses `house.chunkRequests`, `house.chunks` and `house.chunksWith(needle)` from the fixture (every request, and every response under `/panel/chunks/` with its body). With the fake clock installed it lets four minutes pass on Home (the idle screen comes at five) and expects no chunk request; Energy then makes exactly one request, for a chunk holding `ApexCharts`; Climate makes no further one. Weather opened first draws its charts; a blocked chunk gives the toast; Weather reopened while the chunk is held back draws its three charts once (a `MutationObserver` counts the canvases added); and a tap on an energy range tab while the chunk is held back throws nothing. It replaced an earlier version that waited for `networkidle`, which cannot see a fetch that a timer makes later. Checked that it can fail, each by hand and then reverted: importing the library statically from `apex.js` (no chunk at all), calling `loadCharts()` in `build()`, calling it from a 1,500 ms timer in `build()`, dropping the tag check in `weatherSheet` (six canvases) and dropping the guard in `energyMain`.
- **Licence and Renovate.** The `license` field on npm says MIT for every release up to 5.0.0 (3.x, 4.x and 5.0.0) and "SEE LICENSE IN LICENSE.md" / "ApexCharts License" from 5.1.0 (July 2025), so "3.45.2 is the last plain-MIT release" in the first draft of the comments was wrong, and the parent spec's "the exact major where this started was not confirmed" is now answered: 5.1.0. What holds the panel on 3.45.2 is the charts: a minor or patch would redraw what the baselines pin pixel for pixel, and `dist.test.mjs` asserts the version. An exact pin only stops Renovate's majors, and its weekly "npm minor and patch" group would have proposed the 3.x releases that followed, so `renovate.json` has a rule with `allowedVersions: "3.45.2"` for `apexcharts` beside the rule that skips majors; unfreezing is a deliberate change with a changeset and a visual check. `apexcharts` is a runtime dependency, so a pull request that changes it ships and takes no `no-changeset` label; the three places that said the package has no runtime dependencies (`renovate.json`, `changeset.yml`, spec 05) now say so.

## As built (#37)

Mermaid's part of this spec, as it is in the repository. The plan stays as written; this is the record.

- **Mermaid is pinned at exactly 11.4.1, not `^11`.** 11.4.1 is the version that was vendored, and with it the 81 screenshot baselines pass unchanged. The current 11.x, 11.17.2, changes the four full-house Automations screenshots: `auto-tablet-light-en` by 513 pixels, `auto-tablet-light-fr` by 513, `auto-tablet-dark-en` by 436 and `auto-tablet-dark-fr` by 437; the other 77 screenshots, the bare house's Automations tab (no flow) among them, do not move. Bisected with npm builds: 11.4.1 to 11.9.0 match the baselines pixel for pixel; 11.10.0 is the first that does not (611, 613, 477 and 479 pixels on the same four), and a further change between 11.12.2 and 11.16.1 brings it to the figures above. The cause is in Mermaid: from 11.10 the rounded steps and the trigger's stadium are drawn as two `<path>` elements (fill and outline) by its newer shape code instead of one `<rect rx>`, node centres move by up to 0.035 px and edge ends by about half a pixel. The differing pixels are anti-aliasing along node outlines, arrow joins and a few glyphs; nothing a person would see, but the baselines are exact and this pull request ships no visible change. Renovate's `:pinAllExceptPeerDependencies` would have pinned a caret range anyway.
- **What 11.4.1 carries.** `npm audit --omit=dev` reports nine Mermaid advisories for 11.4.1 (two fixed in 11.10.0, four in 11.15.0, three in 11.16.1: XSS in sequence and architecture diagram labels, HTML or CSS injection through `classDef` and the configuration, prototype pollution in the configuration API, endless loops in Gantt and XY charts) and, through `@mermaid-js/parser` 0.3.0 and `uuid` 9, `lodash-es` and `uuid` advisories. The vendored file was the same code, so what ships does not change; it is only visible now. The panel draws flowcharts only, with `securityLevel: 'strict'`; the `classDef` and style values come from the panel's own theme colours, and Home Assistant text reaches the source only inside quoted labels, escaped as the next point describes. Moving to the current 11.x is its own pull request: it re-records the four Automations baselines and says so in a changeset. `renovate.json` gives Mermaid its own group, so a bump comes alone rather than in the weekly group with the dev dependencies (whose `no-changeset` label would also skip the changeset job), and its visual job fails until a person re-records the baselines and adds the changeset on its branch; Renovate does neither. Unlike ApexCharts (#36), Mermaid is not frozen, because its releases carry security fixes.
- **Home Assistant text cannot act as Mermaid syntax.** Step aliases, entity names and trace errors go into the flow's labels. `esc()` already turned `"` into `&quot;`, so no text could close a label (the `#quot;` replace that followed was dead), but Mermaid reads a `%%{init: …}%%` directive anywhere in the source: an alias could switch the theme, add CSS through `themeCSS` (a `url()` there made the browser fetch it) or change label settings, and an unclosed `%%{` cut the label short. `esc2` now writes every `%` as Mermaid's `#37;` entity, which draws as `%`. `test/e2e/automations.spec.ts` serves the test house's automations with four such aliases on the steps of the flow the tab draws (through the fixture's new `automations` option, so the default house and the baselines are untouched) and checks that each shows as typed, that the stylesheet keeps the panel's colours and has no rule from them, and that nothing is fetched outside the house; with the old escaping the directives vanished from the labels, the flow turned to the dark theme and its stylesheet gained the `url()` rule.
- **The npm 11.4.1 resolves newer dependencies than the vendored file bundled** (DOMPurify 3.4.17 instead of 3.2.1, marked 13.0.3, d3 7.9.2). The flow chart's SVG is the same markup apart from the order of attributes, which DOMPurify writes differently, and the same pixels.
- **Chunks.** `import('mermaid')` emits 61 files under `dist/chunks/`, 2,544,796 bytes (746,503 gzipped at level 9, file by file; the vendored `mermaid.min.js` was 2,571,900 and 743,434). Opening the Automations tab fetches 24 of them, 566,771 bytes and 166,870 gzipped, where it fetched the whole file before; the Home tab fetches none. No `manualChunks`: one Mermaid chunk would make the tab download every diagram type again, and neither the harness server nor the release zip minds a folder of files. With #36 merged, the entry is 505,788 bytes (144,650 gzipped at level 9; `npm run size` says 144.64 kB of its 160 kB budget), 339 bytes less than `main` with #36 (506,127 bytes and 144.8 kB): `loadScript` and `BASE` are gone and `import('./chunks/mermaid.core-….js')` takes the place of the old loader call.
- **Source maps: every chunk with code keeps one, without the libraries' text.** Rolldown writes a map for 55 of the 62 chunks (the other 7 hold no code from a source file: re-exports, and its runtime helpers). With `sourcesContent` they were 9.9 MB for Mermaid and 1.1 MB for ApexCharts, and nearly tripled the release zip. A plugin in `vite.config.ts` (`chunk-maps-without-library-sources`) empties `sourcesContent` for every `node_modules` source in `chunks/*.map`, so a stack trace from a chart or a flow still names the library's file and line, without the text. The panel's own files keep theirs: `home-panel.js.map` is unchanged, and a chunk's `src/` sources would keep it too. The chunk maps are 4,153,815 bytes (ApexCharts' 575,544), and the release zip is 2,394,426 bytes, against 1,563,199 on `main` with #36 (whose zip still had `mermaid.min.js` and ApexCharts' full map) and 1,326,602 before #36. This is #76's second option, for both libraries.
- **Licence comments stay in the chunks.** Vite 8 strips legal comments when it minifies; `comments: {legal: true}` keeps the ones the libraries carry (DOMPurify's `@license` header and the svg.js and ApexCharts banners among them), as the vendored files had them. The entry has none and is unchanged by it. ApexCharts' banner is therefore back in its chunk, where #36's As built says the minifier dropped it; its dist test still recognises the chunk by a class name.
- **Loading under Home Assistant.** The entry imports `./chunks/…`, which the browser resolves against the URL `home-panel.js` came from; served under `/local/home-panel/` and `/hacsfiles/ha-home-panel/` with `?v=2.11.1`, the chunks load from beside it and nothing asks for `home-panel.js` without its query. The dist test checks that no chunk imports the entry back, which would load a second copy of the panel's modules.
- **Failure.** When the import fails, each flow box says the flow drawing library didn't load, that the chunks folder is missing next to `home-panel.js` or the connection dropped, and to reload the page (Chromium remembers a failed module for the page's life, as #36 found). The promise is held once per page in `src/auto.js` and `auDraw` awaits it directly, so a second panel shows the hint too; with the `<script>` tag it waited for a load event that had already fired.
- **`loadScript` and `BASE` are deleted.** With ApexCharts (#36) and Mermaid both imported, nothing called them; `grep -rn "loadScript\|window.mermaid\|mermaid.min.js" src` returns nothing, and the `Window` block of `src/legacy/dom-scaffolding.d.ts` is gone with them.
- **The loose type check reaches Mermaid's declarations.** With `import('mermaid')` in `src/auto.js`, `tsconfig.legacy.json` (#35) loads Mermaid's `.d.ts` files, and two of them fail: they import `type-fest`, which Mermaid lists as a dev dependency so npm does not install it, and `@antfu/utils`' declarations (through `@iconify/utils`) do not compile under TypeScript 6. `tsconfig.legacy.json` sets `skipLibCheck`, as `tsconfig.json` already does; the strict `tsconfig.check.json` pass is unchanged.
- **`package-lock.json` is a shipping path.** It pins the libraries the build puts in the chunks (DOMPurify, d3 and the rest inside Mermaid's), so lock-file maintenance can change what ships: `SHIPPING` in `changeset.yml` lists it, and spec 05 and the README say lock-file maintenance needs a changeset when it moved a shipped library, or the label when not.
- **Tests.** `test/e2e/chunks.spec.ts` uses #36's fixture (`house.chunkRequests`, `house.chunks`, `house.chunksWith(needle)`) and its pattern: with the fake clock, four minutes pass on Home and no chunk is asked for; opening Automations fetches the one chunk with Mermaid's core (found by `mermaidAPI`, a property of its default export that minifying keeps) and draws the flow; with the chunks blocked, the flow boxes show the hint. Checked that it can fail, each by hand and then reverted: importing Mermaid statically (the Home tab then asks for the chunks the entry shares with the diagrams), calling the import when `auto.js` loads, and calling it from a 1,500 ms timer in `build()`. The spec's "exactly one request" on Automations is one chunk with the core: Mermaid is 24 requests. The dist test lists `dist/` recursively: chunks are `[name]-[hash].js` and each has its map exactly when it names one; no chunk map carries a library's text, and `home-panel.js.map` carries all of `src/`'s; exactly one chunk has Mermaid's core, with its map, and the entry has none of it; the entry names chunks only inside `import()`; no chunk imports the entry.
- **Release workflow unchanged.** Its zip step lists files recursively on both sides of the `diff`, so `chunks/` is compared file by file; run locally on the merged build, it matches the 121 files and fails when one chunk is left out of the zip.

## As built (#38)

The last step: no committed library files, and a generated licence list. The plan stays as written; this is the record.

- **Leaflet and `vendor/` are gone.** `grep -rni leaflet src` returned nothing before the change and returns nothing after it; `test` and `README.md` matched only before (the README's Develop and Credits paragraphs, and `test/unit/dist.test.mjs`'s list of vendored files), and `docs/` keeps its history. `vendor/` (`leaflet.js`, `leaflet.css`, the hand-written `LICENSES.md`) is deleted, `vite-plugin-static-copy` is uninstalled and its plugin entry removed, and the `vendor/` lines of `eslint.config.js` and `.prettierignore` went with it. `npm run build` emits `home-panel.js`, `home-panel.js.map`, `chunks/` and `LICENSES.md`, and no `assets/` folder (both stylesheets are imported as text); `dist.test.mjs` asserts exactly that list, which fails on any other file.
- **`LICENSES.md` ships inside `dist/`, so it is in the release zip.** Spec AC3 says the file exists at the root and the plan says nothing about the zip; a manual install or HACS gets the zip's files, and a licence list that stays in the repository does not travel with the code it describes. A small plugin in `vite.config.ts` (`ship-licenses`) emits the root file into `dist/` as an asset. Because it is in `dist/`, `release.yml`'s zip step needed no change (the `find` and `unzip -Z1` lists are compared file by file, and run locally on this build they match, 120 files, LICENSES.md among them; the zip is 2,371,727 bytes against 2,394,426 in #37, the 262 KB of licence text more than paid for by Leaflet's 150 KB and the stylesheet). `changeset.yml`'s `SHIPPING` list drops `vendor/` and names `LICENSES.md` in its place, so a pull request that changes the list needs a changeset. `dist.test.mjs` also asserts that `dist/LICENSES.md` is the root file byte for byte.
- **The tool is `license-checker-rseidelsohn` 4.4.2, not 5.0.1.** 5.x requires Node 24 and npm 11; `engines` here is `^22.19 || ^24.5 || >=26` and the lint job runs Node 22. 4.4.2 (Node 18 or later) gives the same fields and the same 148 packages on Node 24 and 26 (the two checked here); Node 18 or later is what its own `engines` ask for. It is a dev dependency at an exact version, as everything else here. Amended in #83: the Node 24 floor made 5.0.1 possible, and it is what the repository now uses (`engines` `^24.5 || >=26`, CI on Node 24); it lists the same 148 packages and `LICENSES.md` came out byte-identical, and Renovate no longer holds back the licence checker's major.
- **No `npx`.** `scripts/licenses.mjs` imports the package's `init` and calls it with `production: true` and `excludePrivatePackages: true`, so it needs no network and runs the installed version. It also exports `collectLicenses()` (the rows: name, version, licence, repository, text) and `renderLicenses(rows)` (the file's text), which the tests use; an `UNKNOWN` licence makes the run-directly block print the message and exit 1. Run directly it writes `LICENSES.md` (or the path given as its first argument).
- **What the list covers: the whole production tree, 148 packages.** `--production` lists every package npm installs for `dependencies`: ApexCharts brings the svg.js family and a spline helper (10 rows with itself, `svg.select.js` in two versions), Mermaid the other 138: DOMPurify, d3 and its parts (with four older copies under `d3-sankey`), dagre-d3-es, khroma, marked, lodash-es (two versions), cytoscape and its layouts, katex, uuid, langium, chevrotain, roughjs and the rest. Vite tree-shakes part of it out of the chunks (Mermaid's `@types/*` packages, 33 of them, hold only declarations; the language server and build helpers are never imported by what the panel draws). The chunk maps name 44 packages by file, and the list was not narrowed to those, because a package inside a pre-bundled file (svg.js inside `apexcharts.esm.js`) has no entry in a map, and what the maps show changes with each Mermaid release. The trade-off: a package that might ship costs a table row and its licence text; one that ships and is missing from the list would be a licence problem. The file says so in its second paragraph, and a test in `dist.test.mjs` asserts that every `node_modules` package named in a chunk map has a row.
- **The file is deterministic.** Rows are sorted by name then version with a plain code point comparison (`localeCompare` depends on the machine's locale); a package installed in two versions has two rows and two texts; licence text has CRLF turned into LF, trailing spaces removed and the ends trimmed; nothing from the checker's `path`, `publisher` or `email` is used, so no absolute path, date or name of a machine is in it. Run twice, the file is identical; run from a fresh `npm ci` in the Playwright image (`mcr.microsoft.com/playwright:v1.63.0-noble`, Linux arm64, Node 24.20) from the same `package-lock.json`, it is identical to the file written on the Mac (Node 26) byte for byte, 261,682 bytes. The production tree is the same as before this change: 151 production entries in the lock file on `main` and in this branch, none at a different version; the lock file gained only the checker and its dependencies.
- **Robust against odd packages, none of which is in the tree today.** A `licenseFile` that is not named `LICENSE*`, `LICENCE*` or `COPYING*` (the checker falls back to a README) is not taken for the text, and the entry says that the package ships no licence file and what its `package.json` declares; a licence array is joined; a missing repository is an empty cell; an `UNKNOWN` or `UNLICENSED` licence stops the script with the package named, so a person reads it; a fence longer than any run of backticks in a text keeps a text with backticks from closing its own block; a `|` in a table cell is escaped. DOMPurify's `(MPL-2.0 OR Apache-2.0)` is shown as the checker gives it, with the one `LICENSE` file that holds both; khroma's `MIT*` (read from its licence file, not declared) is explained by a sentence in the file.
- **The drift tests** are in `test/unit/licenses.test.mjs`. (1) The plan's test: each `dependencies` name in `package.json`, with the version `package-lock.json` has under `node_modules/<name>`, has a `| name | version |` row. (2) Stronger than the plan, and cheap (about 0.3 s): the table's rows equal the installed tree's, compared as objects so a failure names the packages and versions that moved, and then (3) the whole file equals what `renderLicenses()` writes, licence texts included; so a transitive package that moved with the lock file, not only apexcharts or mermaid, fails them. (4) There is no `vendor` directory. Checked that it can fail: `npm install --save-exact mermaid@11.5.0` (package.json and the lock file both move, the file is not regenerated) fails tests 1 and 2 (and 3) with "LICENSES.md has no row for mermaid 11.5.0: run npm run licenses"; reverted with the saved files and `npm ci`. Removing the DOMPurify row fails the `dist.test.mjs` coverage test.
- **What a Renovate bump looks like now.** Exact pins mean a Mermaid bump changes `package.json` and `package-lock.json` and not `LICENSES.md`: the licences test turns the pull request red, and a person runs `npm run licenses`, commits the file and (with the baselines and the changeset #37 already requires) the pull request goes green. Renovate's `postUpgradeTasks` could run the script, but they need a self-hosted Renovate; the README's Renovate paragraph says to run `npm run licenses` instead. Lock-file maintenance that moves a package inside Mermaid fails the same test, as it should: the versions in the file are the versions in the chunks.
- **The notices Vite strips stay.** `comments: {legal: true}` (#37) is in place; this build's chunks carry DOMPurify's `@license` header, the svg.js banners, ApexCharts' banner and the "Bundled license information" block, and `dist.test.mjs` now asserts three of them (DOMPurify's header, svg.draggable.js' banner and ApexCharts' banner) so a Vite upgrade that changes the option fails there.
- **Size.** `npm run size` has two more entries without a `limit`: the ApexCharts chunk (135.33 kB gzipped) and all chunks together (881.83 kB, Mermaid's 62 files and ApexCharts'), printed for information in CI beside the entry (144.65 kB of its 160 kB), as the plan asks. The sizes are `size-limit`'s gzip, which differs a little from Vite's.
- **Renovate.** The ApexCharts major rule (`enabled: false`) and the `allowedVersions: "3.45.2"` freeze are in `renovate.json`, unchanged; Mermaid's group is the one #37 added. The licence checker is a dev dependency, so its bumps take the `no-changeset` label.

- **What ApexCharts 3.45.2 does.** On mount, `apexcharts.esm.js` takes `el.getRootNode()` and, if it is a `ShadowRoot` (or the document has no `<style id="apexcharts-css">` yet), creates a `<style id="apexcharts-css">` with the stylesheet as `textContent` and prepends it to the shadow root (`s.prepend(t.css)`), before the panel's `<style>`; in the document it appends to `<head>` instead. In a shadow root the `isShadow ||` branch never looks for an existing element, so every chart instance adds one; the panel's two Energy charts leave two, and the elements stay when a chart is destroyed. The embedded text is `dist/apexcharts.css` byte for byte (13,065 bytes both; compared as strings in Node and by length in the browser). The panel's own `#apexcss` copy was therefore the same rules again, in the same shadow root, but after the panel's `<style>` instead of before it.
- **The cascade order changed, harmlessly.** The `<style>` elements in the shadow root on the Energy sheet were the library's, the library's, the panel's, `#apexcss` (the old build); they are the library's, the library's, the panel's now. The issue says the cascade is unchanged; that is not exact. Before, the last copy of the library's rules came after the panel's, so the library won equal-specificity ties against the panel's rules; now the panel's rules come after the library's and win them. It makes no difference because only two panel rules touch chart elements, `* {box-sizing}` and `.apexcharts-tooltip {font-family: … !important}`, and neither depends on order (the first sets a property the library's rules do not set on the same elements, the second is `!important`). That is also what the computed-style comparison below shows: no property of any chart element differs, at rest or on hover, on the five sheets, light and dark.
