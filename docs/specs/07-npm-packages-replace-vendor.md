# Spec 07: npm packages replace the committed vendor files

Parent: [production-grade-refactor.md](production-grade-refactor.md), phase 1.
Depends on: [06 Vite build](06-vite-build.md). Independent of [08 bundled font](08-bundled-font.md).
Ships as: one pull request, a patch release, no visible change.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be read as in RFC 2119.

## Problem Statement

ApexCharts 3.45.2, Leaflet 1.9.4 and Mermaid 11.4.1 are committed as minified files under `vendor/` (3.2 MB) and copied beside the bundle at build time. Nothing tells the maintainer about a security fix; the versions in the licences file are maintained by hand; and Leaflet turns out to be unused by the panel itself (the radar map comes from the Weather Radar Card, which brings its own Leaflet), so 150 KB ships for nothing. The lazy loading works by appending `<script>` tags for files found next to the bundle, which ties the file names to the loader.

## Solution

Install ApexCharts and Mermaid from npm at the versions used today, load them with dynamic `import()` so Vite emits them as lazy chunks, drop Leaflet, delete the `vendor/` directory, and generate the licences table from the installed packages. ApexCharts is pinned to its 3.x major, and Renovate is told to ignore its majors because later lines are dual-licensed.

## User Stories

1. As a maintainer, I want Renovate to tell me about a patch to Mermaid or ApexCharts, so that security fixes are not something I have to remember to check.
2. As a maintainer, I want the licences file to be correct by construction, so that it cannot drift from what ships.
3. As a household member, I want the panel not to download a library it does not use, so that the tablet loads less.
4. As a maintainer, I want the chart and diagram libraries to remain lazy, so that the Home tab does not pay for the Automations tab.
5. As a maintainer, I want ApexCharts kept at the last plain-MIT line and protected from an accidental upgrade, so that the repository's MIT licence stays simple.

## Implementation Decisions

### Packages

- `apexcharts` at exactly `3.45.2` (no caret). `mermaid` at the current `11.x` release (caret allowed; Renovate tracks it). Both as `dependencies`, not `devDependencies`, so the licence tooling sees them as shipped.
- Leaflet is NOT installed. `vendor/leaflet.js` and `vendor/leaflet.css` are deleted, the README credit line for Leaflet is removed, and the dist test stops expecting them. The PR description MUST state the verification: `grep -rn leaflet src/` returns nothing before and after.
- The `vendor/` directory and `vendor/LICENSES.md` are deleted.

### Lazy loading

- The `loadScript` helper and its `<script data-home-panel>` mechanism are deleted. The class obtains ApexCharts with `const {default: ApexCharts} = await import('apexcharts')` at the point where it awaited `this.apex` before, and keeps a module-level promise so the import happens once. All references to `window.ApexCharts` are replaced by the imported binding.
- ApexCharts' stylesheet is imported as text (`apexcharts/dist/apexcharts.css?raw`) inside the same lazy module and injected into the existing `#apexcss` style element, replacing the `fetch(BASE + 'apexcharts.css')`.
- Mermaid is obtained with `const {default: mermaid} = await import('mermaid')` where `loadScript(BASE + 'mermaid.min.js')` was, replacing `window.mermaid`. Mermaid's `initialize` call and its `securityLevel: 'strict'` setting are unchanged.
- Vite emits each as a chunk under `dist/chunks/`. The two lazy modules MUST be separate chunks from the entry and from each other; the chunk file names carry a content hash so the HTTP cache needs no `?v=`.
- The static copy plugin from spec 06 is removed.

### Licences

- `vendor/LICENSES.md` is replaced by `LICENSES.md` at the root, generated by `npm run licenses`, which uses `license-checker-rseidelsohn` (or an equivalent that reads `package-lock.json`) restricted to production dependencies and writes a table with package, version, licence and repository URL, followed by the full licence text of each. The Montserrat font row is added by spec 08.
- A Vitest test reads `LICENSES.md` and asserts that every production dependency in `package.json` appears with the exact installed version from `package-lock.json`, so a bump without regeneration fails CI.
- The README's Credits section points at `LICENSES.md` and names ApexCharts and Mermaid only.

### Renovate

- The rule from spec 05 disabling `apexcharts` major updates is confirmed present. A second rule MAY group `mermaid` updates with the other minor and patch updates.

### Size

- The size budget from spec 06 applies to `dist/home-panel.js` only; the lazy chunks are not counted but their gzipped sizes MUST be printed by `npm run size` for information (ApexCharts about 135 KB, Mermaid about 750 KB today).

### Tests

- The dist test asserts: no `vendor` files in `dist/`; exactly one chunk whose content includes the ApexCharts banner and one whose content includes Mermaid's; the entry does not include either library.
- A Playwright behaviour test MUST assert that loading the Home tab triggers no request for a chunk containing ApexCharts or Mermaid, and that opening the Energy tab (charts) and the Automations tab (Mermaid) each trigger exactly one such request. The fixture's network recording is extended to capture chunk URLs for this.
- The screenshot baselines MUST pass unchanged.

## Acceptance Criteria

1. `vendor/` does not exist; `package.json` lists `apexcharts` at `3.45.2` exactly and `mermaid` at `^11`; `grep -rn "leaflet" src test README.md` returns nothing. Amended in #37: `mermaid` is pinned at exactly `11.4.1`, the version that was vendored, because every later 11.x moves the Automations flow charts by a few hundred pixels; see "As built (#37)".
2. `npm run build` emits `dist/home-panel.js`, its map and at least two chunks; the Home tab loads none of the chunks and the Energy and Automations tabs load one each (Playwright test green).
3. `LICENSES.md` exists at the root, is generated, and the licence test passes; bumping Mermaid in `package.json` without regenerating makes the test fail.
4. The visual project passes with no baseline updated; the behaviour suite passes.
5. `renovate.json` contains the ApexCharts major-update rule.

## Testing Decisions

Baselines prove the charts and flow diagrams draw as before. The chunk-loading test protects the lazy behaviour, which is the one thing this change could silently break. The licence test protects the drift this spec exists to end.

## Out of Scope

- Upgrading ApexCharts past 3.x or replacing it.
- Replacing Mermaid.
- Changing any chart option or diagram style.
- The Weather Radar Card dependency, which stays an external HACS card loaded from its Lovelace resource URL.

## Notes

- Mermaid 11 as an ES module is large and pulls in many sub-packages; Vite will split it into several chunks. That is acceptable. If chunk count becomes a problem for the harness server or the zip, use `build.rollupOptions.output.manualChunks` to keep Mermaid in one chunk.
- ApexCharts' package exports both ESM and UMD; make sure the ESM build is picked (Vite does by default) so tree shaking applies.
- Deleting Leaflet is a behaviour-neutral change only because the panel never referenced it; the radar sheet's "didn't load" note in the test house proves the radar comes from elsewhere.

## As built (#37)

Mermaid's part of this spec, as it is in the repository. The plan stays as written; this is the record.

- **Mermaid is pinned at exactly 11.4.1, not `^11`.** 11.4.1 is the version that was vendored, and with it the 81 screenshot baselines pass unchanged. The current 11.x, 11.17.2, changes the four full-house Automations screenshots (`auto-tablet-{light,dark}-{en,fr}.png`) by 513, 513, 436 and 437 pixels; the bare house has no flow and the other 76 screenshots do not move. Bisected with npm builds: 11.4.1 to 11.9.0 match the baselines pixel for pixel; 11.10.0 is the first that does not (611, 613, 477 and 479 pixels), and a further change between 11.12.2 and 11.16.1 brings it to the figures above. The cause is in Mermaid: from 11.10 the rounded steps and the trigger's stadium are drawn as two `<path>` elements (fill and outline) by its newer shape code instead of one `<rect rx>`, node centres move by up to 0.035 px and edge ends by about half a pixel. The differing pixels are anti-aliasing along node outlines, arrow joins and a few glyphs; nothing a person would see, but the baselines are exact and this pull request ships no visible change. Renovate's `:pinAllExceptPeerDependencies` would have pinned a caret range anyway.
- **What 11.4.1 carries.** `npm audit --omit=dev` reports nine Mermaid advisories for 11.4.1 (two fixed in 11.10.0, four in 11.15.0, three in 11.16.1: XSS in sequence and architecture diagram labels, HTML or CSS injection through `classDef` and the configuration, prototype pollution in the configuration API, endless loops in Gantt and XY charts) and, through `@mermaid-js/parser` 0.3.0 and `uuid` 9, `lodash-es` and `uuid` advisories. The vendored file was the same code, so what ships does not change; it is only visible now. The panel draws flowcharts only, with `securityLevel: 'strict'`, from definitions `src/auto.js` builds with escaped labels and the theme's own colours. Moving to the current 11.x is its own pull request: it re-records the four Automations baselines and says so in its changeset. `renovate.json` gives Mermaid its own group for that reason, so a Mermaid bump never rides in the weekly group with the dev dependencies (whose `no-changeset` label would also skip the changeset job).
- **The npm 11.4.1 resolves newer dependencies than the vendored file bundled** (DOMPurify 3.4.17 instead of 3.2.1, marked 13.0.3, d3 7.9.2). The flow chart's SVG is the same markup apart from the order of attributes, which DOMPurify writes differently, and the same pixels.
- **Chunks.** `import('mermaid')` emits 61 files under `dist/chunks/`, 2,541,937 bytes (744,191 gzipped at level 9, file by file; the vendored `mermaid.min.js` was 2,571,900 and 743,434). Opening the Automations tab fetches 24 of them, 565,724 bytes and 165,972 gzipped, where it fetched the whole file before; the Home tab fetches none. No `manualChunks`: one Mermaid chunk would make the tab download every diagram type again, and neither the harness server nor the release zip minds a folder of files. The entry is 505,424 bytes (144,612 gzipped), 18 more than before: `import('./chunks/mermaid.core-….js')` instead of the `loadScript` call.
- **The chunks ship with their source maps**, as the entry does: 54 maps (the other 7 chunks hold no code from a source file: re-exports, and Rolldown's runtime helpers), 9,895,305 bytes, because they carry Mermaid's and its dependencies' sources. The release zip grows from 1,326,194 to 3,624,900 bytes; the tablet never fetches a map unless DevTools is open. Measured alternatives, left for a decision across both libraries: dropping the chunks' maps with a ten-line plugin keeps the zip at 1,336,557 bytes; keeping them without the `node_modules` sources makes them 3,578,271 bytes and the zip 2,293,791. Spec 06's rule against `node_modules` sources is about `home-panel.js.map`, which is unchanged.
- **Licence comments stay in the chunks.** Vite 8 strips legal comments when it minifies; `comments: {legal: true}` keeps the ones the libraries carry (DOMPurify's `@license` header among them), as the vendored file did. The entry has none and is unchanged by it.
- **Loading under Home Assistant.** The entry imports `./chunks/…`, which the browser resolves against the URL `home-panel.js` came from; served under `/local/home-panel/` and `/hacsfiles/ha-home-panel/` with `?v=2.11.1`, the chunks load from beside it and nothing asks for `home-panel.js` without its query. The dist test checks that no chunk imports the entry back, which would load a second copy of the panel's modules.
- **Failure.** When the import fails, each flow box shows the same hint as before, now naming the chunks folder instead of `mermaid.min.js`. The promise is held once per page, so a second panel shows the hint too; with the `<script>` tag it waited for a load event that had already fired.
- **`loadScript` stays** in `src/legacy/globals.js` until #36: ApexCharts is its last caller. `grep -rn "window.mermaid\|mermaid.min.js" src` returns nothing; the `loadScript` part of the issue's check holds once #36 lands.
- **Tests.** The `house` fixture records the chunks the panel fetches (`house.chunks`, URL and body, and `house.chunksWith(needle)`, as #36 has them). `test/e2e/chunks.spec.ts`: on the Home tab no chunk is fetched; opening Automations fetches the one chunk with Mermaid's core (found by `mermaidAPI`, a property of its default export that minifying keeps) and draws the flow; with the chunks blocked, the flow boxes show the hint. Importing Mermaid statically fails the first test (the Home tab then fetches the chunks the entry shares with the diagrams), and so does calling the import when the module loads. The spec's "exactly one request" on Automations is one chunk with the core: Mermaid is 24 requests. The dist test lists `dist/` recursively: chunks are `[name]-[hash].js` and each has its map exactly when it names one; exactly one chunk has Mermaid's core, with its map, and the entry has none of it; the entry names chunks only inside `import()`; no chunk imports the entry.
- **Release workflow unchanged.** Its zip step lists files recursively on both sides of the `diff`, so `chunks/` is compared file by file; run locally, it matches the 121 files and fails when one chunk is left out of the zip.
