# 0016: One element, one shadow root, and the legacy class as its guest renderer

Status: accepted (2026-11-09)

## Context

Phase 3 moves the panel one feature at a time into Lit elements, and for that something must exist that is neither the old class nor a feature: an element that owns the services, receives `hass` from Home Assistant and gives each feature a place to mount, while the old class goes on drawing everything it has not yet given up, pixel for pixel. Until step B the old class was the element: it attached its own shadow root, built its own store, API client and settings, and wrote the whole 200-line frame into the root with `innerHTML`. Two shapes were possible for the new host. The first is an element inside an element: a new `<home-panel>` holding the old class as a second custom element with a root of its own. The stylesheet is one sheet whose selectors span the frame and the panes (`.app.cp .pane`, `.tabsv .rail`), the class looks up ids across the whole frame (`this.$(id)`), the French layer observes one root, and `placePanels` moves the five detail panels between panes and sheets, so two roots would mean two copies of the sheet, a bridge for every id lookup and two observers. The second is one element and one root, with the old class demoted to a renderer that the element drives.

## Decision

`<home-panel>` is a `LitElement` in `src/shell/home-panel.ts`: the composition root (Seemann), the only place that builds the store, the settings and the API client, and a humble object (Meszaros) that holds no rule of its own. It has one shadow root, Lit's default. The old class becomes `LegacyPanel`, a plain class that is not an element and implements the `GuestRenderer` interface of `src/shell/guest.ts`, the strangler fig's interface (Fowler): `connect(ctx)`, `disconnect()`, `hassChanged(change)`, `panelChanged()` and `narrowChanged(narrow)`, plus `toast`, which stays with the guest until the shell owns the toast. The prefactor (#164) that preceded this step gave the class `this.root`, `this.host` and those methods behind one-line forwarders, so this step is new files and deletions, not a rename.

The guest draws into one container of the shell's template, `<div class="guest" style="display:contents">`, and the rule both sides keep is: **Lit binds nothing inside a guest container, and the guest writes nothing outside its containers.** Lit creates the static nodes of a template once and touches only its bound parts afterwards, so nodes the guest inserts into a static container survive every render; `display: contents` gives the container no box, so the layout is the same. The shell never imports the class, because nothing but `src/main.js` may import legacy code (ADR 0011): `src/main.js` calls `registerGuest(() => new LegacyPanel(), CSS)` before it defines the element. The legacy stylesheet travels with the guest for the same reason, since `src/styles.js` is legacy too: the shell adopts it once as a constructed sheet through `finalizeStyles`, shared by every instance, where the class used to write a `<style>` tag into each root. The rules are the same text, so the pixels are the same.

The shell feeds the store and then tells the guest, in `updated`, in the order Home Assistant sets the properties (`hass`, `narrow`, `panel`), which is the order of the setters it replaces (the guest does not exist during the first `willUpdate`, because it is created in `firstUpdated` once its container does). The guest de-duplicates the config on `store.generation`, which the store bumps on a change, and redraws only when it advanced; it holds no copy of `panel` and calls no `setPanelConfig`. The order is kept on purpose, because it makes the first draw happen with the empty config the store starts from and a second one when the panel's config follows, as today. A single draw with the final config is better engineering and is not pixel identical: the guest appends the Mercury-drop filter (`#glass-distortion`) to its container, every later draw wipes it, and `lensAll` does not append it again, so a panel that draws twice never shows the distortion in Chromium and one that draws once does. The baselines record the panel without it. Fixing that is a change of pixels and a pull request of its own (ADR 0003); the shell keeps the order, and the store is seeded with the empty config in the shell's constructor so that a panel with no config is not counted as a config change.

## Consequences

- Every selector, id lookup and observer of the old class keeps working, and so does the legacy stylesheet, because there is still one root. A move deletes methods from the class and adds a folder; nothing is rewritten on both sides.
- The two-panel spec holds by construction: each shell makes its own store, and the guest module's one piece of state is a factory, not a service.
- The interface only shrinks: each step adds the members the spec names for it, each marked with the move that deletes it. When the last move lands, the interface, the registration, the container and `src/shell/guest.ts` are deleted together.
- The guest does not own the shadow root any more, so a rule the shell and the guest both depend on ("write only into your container") is held by convention and review, not by the platform. The legacy class still writes with `innerHTML`, inside its container.
- Lit's comment markers and the `.guest` div are now in the root the French observer watches; `frTree` ignores nodes without text, so the observer is unaffected.
- A reconnect of the element calls `connect` again, which the class tolerates. A change of `hass` now reaches the guest one microtask later than the old setter did (Lit batches property changes into one update), which no spec can see.
- The first draw is still done twice when a config comes, which costs one build of the frame at startup; deleting that, and the filter that a redraw wipes, are the follow-up that changes the glass.
- `registerGuest` is module-level mutable state in the shell, the one such piece, and the element must be defined after it is called: defining first would give the first element no guest and no sheet.
- The shell holds the legacy stylesheet only through the registration, so the dependency rule needs no exception, at the price of one more argument at the registration.
